# 02 方案设计

## 1. 总体架构

```
                     ┌────────────────────────────────────────────┐
                     │              ReActAgent.run()              │
                     │   (src/kb_agent/agent.py,步数上限 8)        │
                     └───────────┬───────────────────▲────────────┘
                    ①动作 JSON    │                   │ ④观察
                                 ▼                   │
                     ┌───────────────────┐   ┌───────┴──────────┐
                     │   决策模型(二选一) │   │  ToolBox.execute  │
                     │ · LLMReActModel   │   │  search / read    │
                     │   (OpenAI 兼容)   │   │  任何异常→失败观察 │
                     │ · MockReActModel  │   │  可注入工具故障    │
                     │   (离线规则策略)   │   └───────┬──────────┘
                     └───────────────────┘           │
                                                     ▼
                                       ┌──────────────────────────┐
                                       │ RetrievalIndex(检索)     │
                                       │ DocStore(8 篇合成文档)   │
                                       └──────────────────────────┘
```

一次问答的完整调用流程:

1. 用户问题(+ 可选对话历史)进入 `ReActAgent.run()`;
2. 循环第 N 步:决策模型基于"问题 + 历史 + 前序步骤观察"输出一个动作 JSON
   (`search` / `read` / `finish`,见 `real_model.py` 的提示词与 `mock_model.py` 的策略);
3. `ToolBox` 执行工具,返回**观察**(成功数据或失败原因;任何异常都被捕获转为失败观察);
4. 观察追加进步骤记录,回到 2,直到模型输出合法 `finish` 或步数耗尽;
5. `finish` 参数经过校验(状态合法、**引用逐字核验**、冲突必须附原文、answered 必须有依据),
   校验不通过则把错误作为观察反馈给模型自我修正;通过则组装最终交付与 Trace。

## 2. 动作与观察协议

模型每步只输出一个 JSON 动作:

```json
{"thought": "一句话决策依据", "tool": "search|read|finish", "params": { ... }}
```

- `search`:`{query, top_k}` → 观察:`{hits: [{doc_id, title, version_date, applies_to, heading, score, snippet}]}`,`snippet` 为逐字句子;
- `read`:`{doc_id, section?}` → 观察:`{doc: {...元数据}, sections: [{heading, text}]}`;doc_id/section 不存在时返回错误观察并列出可用项(模型可据此纠正);
- `finish`:`{status, answer, citations[], conflicts[], gaps[], next_question_to_user, topics[]}`。

`finish` 校验(防幻觉硬约束):

| 校验 | 行为 |
|------|------|
| `status` 不在枚举内 | 拒绝,错误信息作为观察反馈 |
| `quote` 未逐字出现在被引文档 | **剔除该引用**并记录到 `dropped_citations` |
| `answered` 无 answer 且无引用 / `out_of_scope` 无 gaps / `needs_confirmation` 无冲突且无追问 | 拒绝,反馈后让模型补正 |

## 3. 动态决策:模型如何根据观察调整动作

以冲突场景为例(`examples/case2_doc_conflict/trace.md`,4 步):

| 步 | 动作 | 观察摘要 | 调整依据(决策) |
|----|------|----------|------------------|
| 1 | `search "报销 期限"` | 命中 D01/D02 等片段 | 命中多个文档,先读最相关的一篇 |
| 2 | `read D01` | 报销期限条款:"30 天" | 检索片段同时显示 D02 为"15 天",数值不一致 |
| 3 | `read D02` | 报销期限条款:"15 天" | 两个数值都来自原文,构成真冲突 |
| 4 | `finish(needs_confirmation)` | — | 两文档未注明适用范围与优先级 → 列冲突 + 请求确认,不擅自作答 |

其余路径(完整 Trace 见 `examples/`):

- **检索无结果 → 改写重试**:case3、case4 先按主题词查,0 命中后用同义词扩展改写再查一次,仍无结果才 `out_of_scope` 并列出已尝试的查询;
- **上下文追问 → 合并历史主题**:case5 第二轮"那上下班路上的呢?"检索词合并上一轮主题(补贴),命中 D04 交通补贴;
- **工具失败 → 换证据源恢复**:case6 读取 D01 失败 → 改读 D02 → 用 D01 的检索片段(逐字)作为另一侧证据 → 仍能识别冲突(`evidence: snippet`)。

## 4. 检索设计(为什么不用向量库)

- **字符 bigram TF-IDF 余弦相似度**,章节级索引(标题/章节名加权),纯 Python、确定性、零外部依赖。中文制度文本词汇固定,字符 bigram 召回足够稳;8 篇文档规模下毫秒级完成,确定性输出使 Trace 可复现、可测试;
- **命中门槛**:片段必须包含至少一个扩展主题词,或相似度 ≥ 0.10,过滤弱相关(如问题里的"公司"一词),保证"资料外问题"零误召回;
- **查询扩展**:`data/rules.json` 的主题词表 + 口语别名(吃饭→餐补、几天假→年假)+ 同义词(改写用)。它是合成的"业务规则",换掉文档内容后依然成立;
- **代价**:同义改写能力弱于向量检索,长文档(数千篇)需要换 BM25/向量方案 —— 见 05 复盘。

## 5. 冲突判定的关键规则(避免误报)

Mock 策略中,"不同文档数值不同"必须同时满足才判冲突:

1. 两个文档的**章节标题都与问题主题词有交集**(避免把"餐补"和"出差伙食补助"当成同一件事);
2. 数值**单位相同**(30 天 vs 15 天;元 vs 天是不同方面,不是冲突);
3. 同一单位下出现 ≥2 个不同数值(30 天 vs 30 天 = 无冲突)。

这三条同样体现在测试中(`tests/test_conflict.py` 的三个内容替换用例)。

## 6. 双模型路径与 Mock 边界

| 路径 | 触发 | 职责 | 边界 |
|------|------|------|------|
| 真实模型 `LLMReActModel` | 配置 `AGENT_LLM_BASE_URL/API_KEY/MODEL`(OpenAI 兼容) | 每步调用 LLM 输出动作 JSON;输出解析失败会收到格式错误观察并自我修正 | 需要网络与凭据;温度 0.1 |
| Mock `MockReActModel` | 无凭据时 `auto` 回退,或 `--engine mock` 强制 | 确定性规则策略,驱动同一循环骨架与工具 | **只验证流程、工具链路与交付格式,不证明真实模型的决策效果**。它的"决策"是规则而非语言理解,泛化能力有限(如复杂同义句) |

两个模型实现同一个 `decide(question, history, steps, steps_left)` 接口,循环、工具、Trace、校验完全复用 —— 切换引擎不改一行代码。

## 7. 技术取舍

| 选择 | 理由 | 代价 |
|------|------|------|
| **原生实现,不用 Agent 框架** | 循环只有 ~60 行,自研后协议、校验、Trace 完全可控可解释;考核评估的是对决策机制的理解而非框架使用 | 没有框架自带的记忆/重试等设施,按需自建(当前规模不需要) |
| **依赖仅 requests** | 评审环境 `pip install -r requirements.txt` 即可跑,无编译依赖 | HTTP 客户端功能精简(仅 chat/completions + 重试) |
| **CLI 运行方式** | 考核三选一中最易复制执行、最易自动化验证 | 无图形界面(chat 模式可交互演示) |
| **.env 自动加载(自实现 ~20 行)** | 免引入 python-dotenv | 只支持 KEY=VALUE 基本格式 |
| **故障注入做在工具层** | "工具失败"场景可离线、确定性地演示与测试 | 注入模式是预设的,不模拟真实网络故障谱 |

## 8. 步数上限

`AGENT_MAX_STEPS`(默认 8,`--max-steps` 可调)。每步 = 一次模型决策 + 一次工具调用(或 finish)。步数耗尽未结束时返回 `status=unfinished`、`limit_reached=true`、gaps 中明确写"已达最大步数上限,任务未完成"(`tests/test_agent_loop.py::test_step_limit_returns_explicit_unfinished`)。
